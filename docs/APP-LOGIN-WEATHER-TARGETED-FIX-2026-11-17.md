# App 登录无响应与天气有效性：定向修复记录

日期：2026-11-17（Asia/Shanghai）。目标：Glass `1.1.4-glass.8`、Android code `13`。本轮遵循“修复 → 部分功能测试 → 提交 GitHub → 构建并交付安装包”，不执行整套长时间验收，不改变 R1 受控试点定位。

## 1. 问题与证据边界

用户实机反馈为“点击登录后没有打开浏览器，也没有提示”，属于打开浏览器之前的链路，不应直接归因于密码错误。

本轮确认：

- 原登录流程先等待 OIDC discovery、PKCE 和安全存储，再调用 `Browser.open`；discovery、响应 JSON 读取和原生桥接阶段没有应用层截止。网络或桥接不返回时可一直停在浏览器打开之前。隔离诊断使用的是当前真实会话管理器，不会访问外部网络。
- 既有 APK 内含旧局域网默认地址；用户清空 OIDC 后，启动恢复逻辑可能用构建默认值再次补齐。不能在用户更换部署地址后静默混入旧身份服务。
- 复查时曾发现 Docker/80/443 不可用。这是该次检查的实时状态，不足以反推用户点击当时的唯一原因。App 必须对服务停机给出有限等待和明确反馈，而不是假定服务永远在线。
- [再次审核](PROJECT-REAUDIT-2026-11-17.md)中的 RR-01、RR-02 仍需补齐：天气过期后残留绿色，以及 5 分钟温度有效期未贯穿页面生命周期。
- 历史脚本有替换 `Browser.open`、手工递送回调的场景；历史真实协议检查也明确 `actualPhoneVerified=false`。这些结果不能证明用户手机真正打开过系统浏览器。

当前没有连接到可诊断的 Android 真机，因此本轮不宣称已经确认手机默认浏览器/厂商系统限制的唯一根因。

## 2. 已实施的修复

### 2.1 登录准备有界、可见、可取消

两套客户端同步修复 `src/js/auth/oidc-session.js`、主入口和 UI：

| 阶段 | 截止与处理 |
| --- | --- |
| 服务发现及响应体解析 | 共用 8 秒截止；传递 AbortSignal；超时返回 `DISCOVERY_TIMEOUT` |
| 安全存储读/登录事务写 | 3 秒；失败关闭，不绕过安全存储登录 |
| 系统浏览器启动调用 | 3 秒；区分未响应和启动失败 |
| 登录准备总过程 | 15 秒，不包含用户在系统浏览器中输入账号的时间 |
| 回调令牌请求及响应体 | 8 秒；失败返回明确错误，而非无限等待 |

界面显示“连接登录服务 → 准备安全事务 → 打开浏览器 → 等待回调”，并提供取消入口。错误按稳定错误码转换为中文，不将授权码、PKCE verifier、令牌或供应商密钥放入提示/日志。

取消/超时会释放登录占用并隔离旧异步结果；尚未完成的不可取消原生存储写入会阻止新写入，避免覆盖新事务。迟到写入仅清理原事务；不能把 `Promise.race` 误称为原生操作一定已被物理取消。原有 state、nonce、issuer、audience、PKCE 和回调身份检查保留。

同一认证身份下的阶段更新走局部运行态补丁，身份/站点真正变化仍保留必要的上下文重置，不通过整页轮询制造提示。

### 2.2 配置恢复尊重用户选择

- 显式存在的空 OIDC 字段保持为空，不再用旧构建默认值回填。
- 不把另一个服务器的默认身份配置无条件嫁接到当前 API。
- 连接设置增加“填入安装包默认配置”：仅填入草稿，明确提示“尚未保存”，测试并保存后才生效。
- 更新 APK 不静默删除/覆盖已保存端点、蓝牙绑定或用户数据。旧地址需要由用户确认切换。
- 本机交付包的公开端点由私有构建环境提供；这些环境文件、账号密码及供应商密钥不提交 GitHub。

### 2.3 RR-01：过期天气不再给出当前颜色结论

后端 `EXPIRED` / `UNAVAILABLE` 时，温度、湿度、气压、ESD、结露五项当前指标统一不可评估，保留历史读数及更新时间。两客户端 Store 和 UI 另做防御性中性化，顶部提示“上次数据”。正常值的红/黄/绿阈值不变。

### 2.4 RR-02：温度有效期贯穿展示和推送

- API v1 以可选兼容字段 `assessment` 提供服务端评估时间、天气截止和温度来源身份/接收时间/截止；保留旧构造与已有字段，无破坏性版本切换。
- 服务器继续以有效服务端接收时间判断温度：300 秒边界有效，超过即无效；不借用默认设备温度或不可信旧时间。
- App 使用一个一次性定时器处理最近截止，结合服务端时间基线、接收记录与单调经过时间；本机时间回拨不能延长旧结论。恢复前台时重新检查，不新增秒级轮询。
- 相关来源离线/归档时立即局部失效；无关及重复设备事件不产生额外天气查询。仅“重新在线”不会由客户端自行变绿，必须收到新的服务端有效评估。
- 新的设备事件提交后，后端只读取既有天气快照重算，不访问天气供应商；风险等级变化立即推送，同等级的接收时间/有效期续期最多每分钟一次。
- 缓存保留本次接收时间，不把旧快照重新加载到内存误当作刚收到的新结果。退出/换站/销毁会清理旧计时器。

## 4. 交付与现场操作

1. 测试通过后提交到现有 `codex/glass5-remediation` 分支，并核验目标仓库远端提交；不绕过 PR 审核强行替换默认主分支。
2. 提交完成后重新构建 Glass Debug APK，检查包名、版本/code、签名、SHA-256 和包内 `build-info.json` 的源码提交；APK 通过本机交付链接提供，不将 SDK、密钥或 APK 二进制混入源码提交。
3. 旧安装用户进入“连接设置”，点击“填入安装包默认配置”，核对 API / WSS / Issuer / Client ID / 回调，测试后“保存并切换”。该按钮不会自行覆盖服务器或登录。
4. 系统浏览器需能够访问身份服务并信任本机 CA；App 内置 Debug CA 信任不等于手机外部浏览器自动信任该证书。错误必须可见，但不关闭证书验证、PKCE 或站点授权来掩盖错误。
5. 本机测试栈复用原有数据兼容的基础镜像，后端换为本轮 JAR；不把此启动冒充当前生产镜像全量升级或不可变发布验收。

## 5. 明确保留的验收边界

尚未执行本轮 APK 在用户手机上的真实浏览器拉起、账号输入、温/冷启动回调、厂商电池策略、GPS/BLE、弱网长时间运行、Release 签名、nRF52840 板卡和生产恢复/压力验收。浏览器故障用例有意隔离原生边界，不能替代这些实机项。

RR-01/RR-02 的本轮实现与定向自动化闭环已有证据，但不能因此把整个项目或真实手机登录状态改称“全部验收通过”。AUD-04/AUD-05 的主分支审批和正式发布门禁仍独立生效；当前定位仍是 R1 受控试点候选。
