# IoT Manager 上线整改方案

日期：2026-10-18。输入基线：`fb0ac983048ee4d10d42e82d06427b878c76e100`；评估依据：[总览测试报告](PROJECT-RELEASE-READINESS-2026-10-18.md)。本文件是整改设计，不是发布批准。

## 1. 目标与范围

保持 Spring Boot / PostgreSQL / Edge Agent / Vite / Capacitor 现有框架，优先消除数据兼容和验证链缺口。Glass Next 保持独立目录、独立 applicationId，不替换原客户端。AI 与知识库继续默认关闭；启用它们需要另行取得真实供应商验收证据。

交付分为仓库内可完成的开发、可在隔离环境执行的验证、需要真实设备或管理资源的验收。只有第三类证据也齐全，才能给出 GO。代码审核通过只允许进入开发。

## 3. 关键技术决策

### 3.1 时间与历史数据

新增全局 `hibernate.jdbc.time_zone=UTC` 后，旧的无时区 LocalDateTime 字段可能经 JVM 默认时区与 JDBC Calendar 再次转换。整改优先移除这一全局转换，验证 `Instant` 的 Hibernate UTC 类型仍保持绝对时间。不能把权威时间改回本地时钟，也不能统一给接口补八小时。

已写错的历史行不能通过代码修复自动恢复。增加只读 PostgreSQL 差异核对 SQL：仅比较已有权威 UTC 对应列与指定、可证明的旧部署时区；没有 UTC 的行不推断。输出修复清单，待备份、停写窗口和逐批核对后另行审定数据修复。此次开发不自动改写生产历史数据，不修改已应用的 Flyway 文件。

### 3.2 App 回退的准确含义

已发布的原始 v2 旧包无法被新代码追溯修复。支持的路线是“旧业务代码 + 兼容 schema 打开器 + 已修复构建依赖”重新签名形成兼容回退包。其 applicationId、证书与当前包一致，versionCode 必须大于已安装包，Android 视为正常升级。原始旧 APK、`adb -d` 或删库重装不能算上线回退能力。

兼容打开器先按调用方要求升级；仅在 VersionError 时无版本打开已有库，检查版本范围、store/keyPath/index，并在 versionchange 时关闭连接。未知版本拒绝读写，失败不删库。回退包生成器校验基线 SHA 与导出路径，输出新目录和来源清单，拒绝覆盖已有目录。旧代码与兼容代码的来回读写测试必须使用真实旧缓存实现。

### 3.3 工具链与浏览器兼容

选择 Vite 7.3.7，匹配当前 Node 22.23.3；保持既有浏览器目标 Chrome/Edge 87、Firefox 78、Safari 14，防止 Vite 升级默认抬高 WebView 需求。仅使用官方 npm registry 执行审计，保留全局镜像配置。所有平台仍使用各自 package-lock，不使用 `audit fix --force`。

依据：[Vite 7 迁移与浏览器目标](https://v7.vite.dev/guide/migration.html)、[Windows 文件访问绕过修复公告](https://github.com/vitejs/vite/security/advisories/GHSA-fx2h-pf6j-xcff)。版本在实施时再次由 npm 官方 registry 验证。

## 4. 发布证据与失败策略

同一候选必须具备：准确源码 SHA/干净构建、严格 CI 零失败零意外跳过、完整依赖安全审计、不可变镜像及扫描、N→N−1→N 数据兼容、备份/PITR/回退证明、已签名 APK 身份、实机验收、容量长稳与运维批准。候选变更使相关旧证据失效；历史通过结果不代替当前结果。

只读预检检查默认分支保护和实际 required checks、禁止 force push/deletion、管理员约束、发布/恢复/回退环境的审核或等价保护、恢复 runner 标签与在线状态。API 403/404、不可读和空配置都不作通过。检查结果不自动宣称已具有恢复能力，也不自动修改仓库权限。

签名工作流只接收完整 SHA 和合法版本号，固定从受信任默认分支运行；源码必须是受保护默认分支的提交。环境 `android-release` 配置四项密钥材料及每个 app 的可信证书 SHA256。私钥只写临时目录，始终清理；仅上传 APK/AAB 与非敏感身份清单。工作流成功不自动发布商店或生产。

## 5. 实施顺序与完成判定

1. 完成方案审核，关闭所有影响实施安全性的设计问题。
2. 完成开发文档与第二次审核，明确接口、失败行为和测试命令。
3. 修复 R1/R2；先证明回归测试能捕获旧缺陷，再修复并回归。
4. 完成 R3/R4/R5/R6 的仓库开发，执行四端单测、构建、浏览器、Java、原生可执行测试和发布工具负例测试。
5. 在可用的隔离 Docker/CI 中执行真实 PostgreSQL 与版本切换；不可用则明确标为待验，不能以 H2 代替。
6. 汇总实际执行结果与外部待办。R5/R6/R7/R8 缺少真实证据时仍为 NO-GO，继续具备条件的工作。

实机验收至少覆盖：目标最低配置手机与实际 PDA、登录/登出/租户切换、BLE 权限拒绝与重新授权、配对/命令确认/断连恢复、局域网 HTTPS/证书链、WSS 重连、冷/热启动、旋转/后台/大字/减少动态效果、离线缓存不串账号、升级及兼容回退后数据完整。真实设备名单、业务成功率、长稳时长和 RPO/RTO 由发布责任人确认后作为批准依据，不在程序中伪造。
